# Проверки pull request

Workflow `Project checks` запускается для pull request, push в main и вручную. Доступ GitHub token ограничен чтением содержимого; credentials checkout не сохраняются. Workflow не использует production secrets, не развёртывает сайт и не загружает `.env` в артефакты.

## Quality and browser tests

Устанавливаются Node 22 и pnpm 11.25.0. Из `.env.example` создаётся временный `.env` со случайными тестовыми JWT/S3-ключами; рабочие или production-ключи не нужны. Проверяются lockfile, lint, unit/component tests, воспроизводимость OpenAPI и клиента, production build и TypeScript. Затем запускаются Chromium и браузерные сценарии:

- UI, безопасный редирект, две вкладки и выход — `playwright.ci.config.ts`;
- публичные нужды — `playwright.needs.config.ts`;
- календарь — `playwright.calendar.config.ts`;
- управляемые информационные страницы — `playwright.pages.config.ts`.

Браузерные проверки используют синтетический API. Настоящая серверная логика проверяется отдельным заданием. SSR-проверки подтверждают использование серверной первой страницы: календарь обходится без дополнительного запроса, нужды сохраняют список при ошибке клиентского обновления. Отдельные сценарии отключают JavaScript и проверяют видимые материалы CMS, пустой и заполненный календарь, нужды, мобильную навигацию и защиту личных разделов. Проверяются также отключённые до гидратации контактные поля и штатная отправка формы после подключения обработчиков.

## Backend integration

Backend-проверка выполняется параллельно с quality на отдельном runner; успешный итог workflow требует прохождения обоих заданий. Docker Compose поднимает PostgreSQL, Redis, MinIO и Mailpit. MinIO собирается из официального исходного релиза существующим Dockerfile. `minio-init` создаёт закрытый тестовый бакет. `pnpm test:e2e` создаёт отдельную БД `club_test_*`, применяет миграции, выполняет весь backend E2E и удаляет временную БД. В конце Docker volumes удаляются на этом одноразовом GitHub runner.

После E2E собирается `Dockerfile.api`, общий для HTTP API и daemon. `scripts/check-runtime.mjs` запускается внутри образа с `--network none`: проверяет замкнутость символических ссылок, наличие worker/HTTP entrypoint и Prisma-миграций, выполнение Prisma CLI/schema engine, импорт shared и ответ настоящего Nest HTTP-сервера на health. Smoke test использует отдельную тестовую конфигурацию и offline-провайдеры, без реальных Telegram/SMTP/БД. Так CI обнаружит зависимость runtime-пакета от файлов исходного workspace.

Отдельный тест намеренно создаёт PostgreSQL deadlock между двумя транзакциями и проверяет, что механизм повторов распознаёт ошибку Prisma/адаптера и позволяет обеим операциям завершиться.

Реальная доставка Telegram, внешний SMTP и внешний S3 этим workflow не подтверждаются. Ни тестовый Telegram-вход, ни credentials из этого workflow не предназначены для production.

## Локальный запуск

В backend-задании `TEST_BROWSER=true pnpm test:e2e` дополнительно запускает `scripts/check-user-flow.mjs` до удаления временной БД. Проверяется собранный Next.js через настоящий Nest HTTP API и PostgreSQL: календарь → вход → обязательный профиль → возврат к событию → запись → перезагрузка кабинета → отмена → повторная перезагрузка. Кандидату запрещены административный API, раздел куратора и событие только для волонтёров. Администратор проходит настоящий challenge с кодом и открывает таблицу пользователей. Внешнее подтверждение Telegram выполняется существующей test-only точкой, письмо перехватывается тестовым провайдером; реальные Telegram и SMTP не используются. Скрипт разрешён только с локальной временной БД `club_test_*`, не подменяет ответы API и проверяет отсутствие ошибок гидратации на мобильном экране. Для локального запуска этого режима сначала соберите web с `PUBLIC_API_URL=http://127.0.0.1:4000` и установите Chromium.

```sh
pnpm lint
pnpm test
pnpm gen:api
pnpm build
pnpm typecheck
pnpm --filter @club/web exec playwright install chromium
pnpm --filter @club/web exec playwright test --config playwright.ci.config.ts
pnpm --filter @club/web exec playwright test --config playwright.needs.config.ts
pnpm --filter @club/web exec playwright test --config playwright.calendar.config.ts
pnpm --filter @club/web exec playwright test --config playwright.pages.config.ts
```

Для полного backend E2E нужна локальная инфраструктура из docker-compose.yml и `pnpm test:e2e`. При собственном Chromium задайте CHROME_PATH; по умолчанию используется установленный Playwright браузер на любой ОС.

## Облачный мониторинг production

`Monitor Qamqor production` проверяет production после успешной публикации и вручную (`mode=now`). При repository variable `QAMQOR_MONITOR_CLOCK_ENABLED=true` он поддерживает одну цепочку проверок с паузой 30 минут: после каждой проверки GitHub token создаёт следующий `workflow_dispatch` с `mode=clock`. Следующий запуск ждёт timer окружения `qamqor-monitor-clock`; runner выделяется после ожидания. Cron `17,47 * * * *` остаётся резервным запуском и восстанавливает отсутствующую цепочку. Ожидающий clock не блокирует немедленные проверки.

Используются только доверенный main-коммит workflow и официальный Vercel CLI 65.10.0; существующий `VERCEL_TOKEN` передаётся только шагу проверки, зависимости приложения не устанавливаются. Только отдельное задание `next` имеет `actions:write` через короткоживущий `GITHUB_TOKEN`; Vercel token ему недоступен. Оно сериализует планирование, проверяет ожидающие запуски и не создаёт второй clock. Ошибка health не прерывает цепочку; намеренная отмена запуска прерывает её до следующего резервного/ручного запуска.

Окружение `qamqor-monitor-clock` должно иметь wait timer ровно 30 минут и единственное branch rule `main` (тип branch), без reviewers или custom protection apps. Перед созданием следующего запуска эти правила проверяются через API; отсутствующий/изменённый timer блокирует цепочку, чтобы исключить быстрый цикл. `deployment: false` не создаёт фиктивных GitHub deployment records. Зависший дольше 75 минут или дублированный clock вызывает ошибку: отмените старые clock-запуски и выполните `mode=now`.

Для проверки механизма есть отдельное окружение `qamqor-monitor-clock-test` с timer 1 минута и тем же правилом `main`. Ручной `mode=clock-test`, `test_checks=2` выполняет ровно две реальные проверки production, затем останавливается независимо от enable switch. `test_failure=true` намеренно завершает первую проверку с ошибкой **после** проверки production: так проверяются продолжение после сбоя и уведомление Actions без остановки приложения. Продолжение не наследует флаг намеренной ошибки. Для остановки регулярной цепочки установите `QAMQOR_MONITOR_CLOCK_ENABLED=false` и отмените ожидающий clock; немедленные и резервные проверки сохраняются.

Проверяются `/api/v1/health`, публичная статистика с обращением к БД, Ready/Alive всех ожидаемых экземпляров worker именно текущего production-деплоя и runtime-ошибки за последние 40 минут. Переходные сбои проверяются повторно три раза. Неизвестный формат ответа или неполные логи означают неуспешную проверку. Содержимое runtime-логов, ответы ошибок и секреты не выводятся. Процесс ничего не перезапускает, не удаляет и не меняет в инфраструктуре.

При устойчивом сбое workflow завершается с ошибкой. Отдельный `Notify Qamqor monitor failures` открывает одну issue с упоминанием и назначением `@NBTRL`; повторный сбой не создаёт новых сообщений. После успешной проверки issue закрывается с ссылкой на восстановление. Тестовая цепочка использует отдельную явно помеченную issue. Обрабатываются только завершения фиксированного monitor workflow из main этого репозитория; задания PR и произвольный код не исполняются. Позднее событие старого запуска не меняет более свежий результат. У задания уведомлений есть `issues:write`, но нет Vercel token или прав запуска Actions. Содержимое логов в issue не передаётся. Обычный успешный запуск не создаёт сообщений, намеренная отмена не считается сбоем.

Стандартные письма Actions привязаны к автору запуска и не гарантируют доставку владельцу для продолжений от бота. Канал issue использует личные настройки упоминаний/назначений GitHub (Email и/или web); доставка почты также требует её доступности. Основная цепочка не требует доставки отдельного cron-события каждые полчаса. Интервал равен 30 минутам плюс время проверки и выделения runner; доступность GitHub Actions по-прежнему необходима, гарантии обнаружения за 30 минут нет. Ready/Alive worker подтверждает состояние процесса, но не доставку каждого уведомления в Telegram.

## План очистки закрытых preview

`Plan closed Qamqor previews` после закрытия PR или ручного запуска с номером закрытого PR формирует список его preview-деплоев. Для привилегированного события `pull_request_target` выполняется только доверенная main, код PR не запускается. Открытые PR, fork PR, production, активные сборки и сохранённый preview PR #20 блокируют планирование.

Это только план: workflow и `scripts/preview-cleanup-plan.mjs` не содержат операций удаления. Автоматическое удаление новых окружений не включено. Перед применением списка нужно проверить зависимости Neon и получить подтверждение конкретных ресурсов. Для Vercel-managed интеграции удаление последнего preview-деплоя ветки вызывает удаление соответствующей ветки Neon вместе с её данными; одного закрытия PR недостаточно.
